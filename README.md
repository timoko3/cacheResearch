# Cache Research

## Настройка, сборка и запуск

Все команды выполняются из корня проекта.

```sh
cmake --preset debug
cmake --build --preset debug --parallel
```

#### Сборка тестов:
```
cmake --preset debug
cmake --build --preset debug
```
#### Запуск тестов:
```
ctest --test-dir build/Linux/debug --output-on-failure
```
Для запуска конкретной группы (к примеру, CacheREF):
```
./build/Linux/debug/cache_tests --gtest_filter='CacheREF*'
```

#### Сборка бенчмарков кешей:
```
cmake -S . -B build-benchmark -DCMAKE_BUILD_TYPE=Release
cmake --build build-benchmark --target cache_benchmark_runner -j
```
#### Запуск бенчмарков:
```
python3 ./cacheBenchmarks/cache_benchmark.py --runner ./build-benchmark/cache_benchmark_runner
```

##### Доступные параметры:

- `--runner PATH` — путь к исполняемому файлу `cache_benchmark_runner`;
- `--root PATH` — директория для сгенерированных конфигураций и входных данных. По умолчанию `./cacheBenchmarks`;
- `--requests N` — количество запросов в одном benchmark-запуске. По умолчанию `20000`;
- `--seeds N [N ...]` — набор seed'ов, для которых выполняются тесты. По умолчанию `1 2 3`;
- `--output PATH` — путь к итоговому CSV-файлу. По умолчанию `./cacheBenchmarks/cache_benchmark_results.csv`.

## Формат входных файлов

Программа принимает два файла: конфигурацию кеш-системы и входные данные теста.

### Файл конфигурации

Первое значение — количество уровней кеша. После него должны идти стратегии вытеснения для каждого уровня в порядке от `L1` к последнему уровню.

Пример `configs/config_1.txt`:

```text
4
LFU
LRU
LIRS
2Q
```

Для этого примера создаётся кеш-система из 4 уровней:

```text
L1 -> LFU
L2 -> LRU
L3 -> LIRS
L4 -> 2Q
```

Разделителями между значениями могут быть пробелы, табы и переводы строк.

### Файл входных данных

Сначала указываются размеры всех уровней кеша. Количество размеров должно совпадать с количеством уровней из файла конфигурации.

После размеров указывается количество запросов, а затем — сами запросы.

Пример `inputs/input_1.txt`:

```text
3 4 5 7
5
1 2 3 2 1
```

Для конфигурации из 4 уровней это означает:

```text
Размеры уровней: 3 4 5 7
Количество запросов: 5
Запросы: 1 2 3 2 1
```

Количество запросов в файле должно совпадать с указанным значением.

## Запуск

Все команды выполняются из корня проекта.

Сначала настроить и собрать проект:

```sh
cmake --preset debug
cmake --build --preset debug --parallel
```

Затем запустить программу, передав первым аргументом файл конфигурации, а вторым — файл входных данных:

```sh
./build/Linux/debug/bin/Debug/cache_research configs/config_1.txt inputs/input_1.txt
```

Общий вид запуска:

```sh
./build/Linux/debug/bin/Debug/cache_research <config_file> <input_file>
```
## Поиск наиболее эффективной системы кешей

Для поиска наиболее эффективной конфигурации были проверены **205 вариантов кеша**. Рассматривались одноуровневые, двухуровневые и трёхуровневые системы с общей вместимостью **64 страницы**:

* одноуровневая: `64`;
* двухуровневые: `8+56`, `16+48`, `32+32`;
* трёхуровневая: `8+16+40`.

На каждом уровне могла использоваться одна из пяти стратегий: **LRU, LFU, ARC, 2Q или LIRS**. Поэтому общее количество конфигураций равно:

```text
5 + 3 · 5² + 5³ = 205
```

Каждая конфигурация проверялась на последовательности из **20 000 запросов**. Для случайных паттернов использовались три разных начальных значения генератора (`seed`), после чего результаты усреднялись. Перед каждым запуском кеш был пустым, то есть учитывался холодный старт.

Для оценки использовались следующие стоимости обращения:

| Место обращения | Стоимость |
| --------------- | --------: |
| L1              |         1 |
| L2              |         5 |
| L3              |        20 |
| Основная память |       100 |

Основной метрикой являлось среднее время доступа — **AMAT**:

```text
AMAT = общая стоимость обработки запросов / количество запросов
```

Чем меньше AMAT, тем эффективнее конфигурация. Дополнительно измерялись процент попаданий и количество обращений к основной памяти.

В качестве теоретического эталона использовался одноуровневый кеш **REF64** вместимостью 64 страницы. Это идеальный алгоритм, который заранее знает всю будущую последовательность запросов и при вытеснении выбирает страницу, обращение к которой произойдёт позже остальных. В реальной системе такой алгоритм использовать невозможно, но он позволяет оценить, насколько практические стратегии отличаются от наилучшего результата.

### Рассматриваемые паттерны

| Паттерн          | Описание                                                                                                       |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| `small_cycle`    | Циклические обращения к 32 страницам. Все страницы помещаются в кеш.                                           |
| `boundary_cycle` | Циклические обращения к 65 страницам. Рабочее множество превышает вместимость кеша всего на одну страницу.     |
| `scan`           | Последовательный проход по 256 страницам. Проверяет устойчивость кеша к длинному сканированию.                 |
| `hot_cold`       | 90% запросов приходятся на 8 часто используемых страниц, остальные 10% — на случайные холодные страницы.       |
| `hot_scan`       | Обращения к небольшому набору горячих страниц чередуются с последовательным сканированием новых страниц.       |
| `phase_change`   | Набор горячих страниц периодически изменяется. Проверяет скорость адаптации стратегии.                         |
| `bursts`         | Новая случайная страница выбирается раз в 16 запросов, а между сменами многократно используется одна страница. |
| `uniform`        | Равномерные случайные обращения к 256 страницам без явно выделенного горячего множества.                       |

### Результаты

В таблице приведены результаты идеального кеша, лучшей практической конфигурации и лучшей многоуровневой системы для каждого паттерна.

| Паттерн          | REF64, AMAT / hit | Лучшая конфигурация  |       AMAT / hit | Отставание от REF | Лучшая многоуровневая |   AMAT | Отставание от REF |
| ---------------- | ----------------: | -------------------- | ---------------: | ----------------: | --------------------- | -----: | ----------------: |
| `small_cycle`    |   1.160 / 99.840% | LRU64, LFU64, ARC64  |  1.160 / 99.840% |            0.000% | LRU32+LRU32           |  1.168 |            0.690% |
| `boundary_cycle` |   2.880 / 98.120% | LIRS64               |  4.385 / 96.615% |           52.257% | LIRS32+LIRS32         |  8.691 |          201.762% |
| `scan`           |  76.430 / 24.570% | LIRS64               | 76.585 / 24.415% |            0.203% | LIRS32+LIRS32         | 81.520 |            6.660% |
| `hot_cold`       |   8.287 / 92.713% | ARC64                | 10.452 / 90.548% |           26.126% | LFU16+LIRS48          | 10.967 |           32.345% |
| `hot_scan`       |  26.000 / 75.000% | LFU64, ARC64, LIRS64 | 26.000 / 75.000% |            0.000% | LFU16+LRU48           | 27.250 |            4.808% |
| `phase_change`   |   8.647 / 92.353% | LFU64                | 10.762 / 90.238% |           24.460% | LFU32+ARC32           | 11.376 |           31.567% |
| `bursts`         |   3.818 / 97.182% | LRU64, ARC64, LIRS64 |  5.707 / 95.293% |           49.454% | LFU8+LRU56            |  6.074 |           59.066% |
| `uniform`        |  41.525 / 59.475% | LRU64                | 75.810 / 25.190% |           82.565% | LFU16+LRU48           | 80.929 |           94.891% |

На паттерне `small_cycle` все необходимые страницы помещаются в кеш, поэтому большинство стратегий после первых 32 промахов практически всегда дают попадания. Сложнее всего оказался `boundary_cycle`: рабочее множество превышает вместимость всего на одну страницу, но обычные алгоритмы не могут заранее определить, какую страницу выгоднее вытеснить.

На последовательном сканировании LIRS64 почти повторяет результат идеального кеша — разница в AMAT составляет только **0,203%**. Для `hot_scan` стратегии LFU, ARC и LIRS также достигли результата REF64. На случайном паттерне `uniform` эффективность всех практических алгоритмов заметно ниже, поскольку в запросах отсутствует выраженная локальность.

Многоуровневые системы обычно имеют более высокий AMAT, даже если обеспечивают сопоставимый процент попаданий. Причина заключается в том, что при промахе на L1 приходится дополнительно обращаться к L2 и L3, а каждое такое обращение увеличивает суммарную стоимость.

### Итоговый рейтинг

Для каждой конфигурации было рассчитано среднее отставание от лучшего практического результата на каждом паттерне:

| Место | Конфигурация  | Среднее отставание |
| ----: | ------------- | -----------------: |
|     1 | LIRS64        |             0.549% |
|     2 | LIRS32+LIRS32 |            19.696% |
|     3 | LIRS16+LIRS48 |            50.443% |
|     4 | LIRS8+LIRS56  |            65.679% |
|     5 | ARC8+LIRS56   |           109.701% |

В рамках выбранной модели наиболее эффективной конфигурацией оказался одноуровневый кеш **LIRS64**: его среднее отставание от лучшего результата для каждого паттерна составляет всего **0,549%**. Среди многоуровневых систем лучший результат показала конфигурация **LIRS32+LIRS32**, однако её среднее отставание уже достигает **19,696%**. Это связано с тем, что обращение к следующим уровням кеша требует дополнительного времени.

При этом оптимальная стратегия зависит от характера запросов: LIRS лучше работает на циклических обращениях и последовательном сканировании, а LRU, LFU и ARC показывают хорошие результаты при локальности и наличии часто используемых страниц. Сравнение с идеальным кешем REF64 показывает, насколько реальные алгоритмы уступают теоретическому решению, которое заранее знает будущие запросы. Таким образом, для рассмотренных паттернов наиболее удачным компромиссом является **одноуровневый кеш LIRS размером 64 страницы**.
