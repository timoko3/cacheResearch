# Методика исследования кеширования

[Оглавление](README.md) · [Обзор экспериментов](conclusions.md)

Исследование сравнивает алгоритмы вытеснения при изменении вместимости кеша,
распределения памяти между уровнями и стоимости обращения к ним.
Рассматриваются три самостоятельные модели.

| Эксперимент | Что подбирается | Что минимизируется |
|---|---|---|
| [Влияние размера кеша на выбор алгоритма](software.md) | Алгоритм одного уровня при каждой вместимости | Число загрузок из источника |
| [Иерархия, приближённая к процессорной](hierarchy.md) | Размеры трёх уровней и алгоритмы при заданных ограничениях | Средняя стоимость запроса |
| [Иерархия с бесплатным обращением к уровням](unrestricted.md) | Число уровней, их размеры и алгоритмы при заданном общем объёме | Число загрузок из источника |

## Термины и общие условия

**Объект** — единица данных с уникальным идентификатором.
В процессорной модели объект называется страницей. Все объекты имеют одинаковый
размер. Запрос указывает, какой объект требуется получить.

**Вместимость** — максимальное число объектов, одновременно хранимых в кеше.
Служебные структуры алгоритма и история идентификаторов вытесненных объектов
в эту вместимость не входят. Поэтому одинаковая вместимость не означает
одинакового полного расхода памяти реализациями.

**Попадание на уровне** означает, что объект найден в этом кеше.
**Промах на уровне** означает, что объект передаётся на поиск следующему уровню.
**Загрузка из источника** нужна только при отсутствии объекта на всех уровнях.
Для одноуровневого кеша каждый промах приводит к такой загрузке.

**Конфигурация** задаёт число уровней, вместимость и алгоритм каждого уровня.
Запись LRU(56) → LIRS(234) обозначает два уровня общей вместимостью 290 объектов.

Все кеши начинают обработку последовательности пустыми. Первые загрузки входят
в результат; отдельный период предварительного заполнения не выделяется.
В пределах одного эксперимента конфигурации сравниваются на одинаковых запросах.
Изменение вместимости не меняет ни порядок запросов, ни набор доступных объектов.

**Начальное значение генератора** определяет воспроизводимую случайную
последовательность при фиксированных параметрах генерации. Значения 1, 2 и 3
обозначают разные варианты случайных запросов, а не разные размеры кеша.
Для детерминированных последовательностей это значение не влияет на запросы.

### Алгоритмы вытеснения

Алгоритм вытеснения выбирает объект для удаления, когда кеш заполнен.

| Алгоритм | Основная идея |
|---|---|
| LRU | Удалять объект, к которому дольше всего не обращались |
| LFU | Удалять объект с наименьшим счётчиком обращений с момента его загрузки |
| ARC | Адаптивно распределять память между недавно и повторно использованными объектами |
| 2Q | Отделять недавно загруженные объекты от объектов с подтверждённым повторным использованием |
| LIRS | Оценивать повторное использование объектов с учётом интервалов между обращениями и истории запросов |

Сравнение относится к конкретным реализациям этих алгоритмов в исследовании.
2Q и LIRS допускаются только при вместимости не менее двух объектов.
Результаты не описывают все возможные реализации алгоритмов с такими названиями.

### Обработка запросов в иерархии

Запрос сначала поступает на L1. При промахе вызывается L2, затем следующий
уровень, вплоть до внешнего источника. При попадании дальнейший поиск прекращается.
Полученный объект помещается в вышележащие кеши, на которых произошёл промах.

Нижний уровень видит только промахи верхнего. Попадание в L1 не обновляет
историю обращений в L2. Поэтому алгоритмы на уровнях подбираются совместно:
изменение верхнего кеша меняет входные запросы нижнего.

Копии одного объекта могут находиться на нескольких уровнях.
Сумма вместимостей ограничивает число занятых мест, а не число разных объектов.
Вытеснение на одном уровне не вызывает автоматического удаления копий
с остальных уровней.

## Последовательности запросов

В таблице приведены параметры последовательностей, использованных в отчётах.
Часто запрашиваемый набор объектов называется **горячим множеством**.
Масштаб генерации фиксирован и не зависит от вместимости проверяемого кеша.

| Вид запросов | Идентификатор в данных | Построение последовательности |
|---|---|---|
| Цикл 145 объектов | small_cycle | Повторяющийся обход 145 объектов в одном порядке |
| Цикл 291 объекта | boundary_cycle | Повторяющийся обход 291 объекта в одном порядке |
| Последовательный проход | scan | Повторяющийся обход 1160 объектов |
| Постоянное горячее множество | hot_cold | С вероятностью 90% выбирается один из 36 горячих объектов, иначе — объект из отдельного набора из 1160 объектов |
| Горячие объекты и сканирование | hot_scan | 384 случайных обращения к горячему множеству из 36 объектов чередуются со 128 обращениями к новым объектам |
| Смена горячего множества | phase_change | Правило 90%/10% сохраняется, но горячее множество меняется каждые 2000 запросов между четырьмя непересекающимися наборами по 36 объектов |
| Серии повторных запросов | bursts | Случайно выбранный из 1160 объектов повторяется 16 раз подряд |
| Равномерные случайные запросы | uniform | Каждый из 1160 объектов выбирается с одинаковой вероятностью |
| Неравномерная популярность | popular | Для 1160 объектов вероятность выбора объекта с номером k пропорциональна 1/(k+1), начиная с k = 0 |
| Переходы между страницами | navigation | Детерминированная последовательность обращений к общим и отдельным ресурсам страниц |

Первые восемь видов используются во всех трёх экспериментах.
Неравномерная популярность и переходы между страницами дополнительно входят
в одноуровневый эксперимент и эксперимент с бесплатным обращением к уровням.

В модели переходов между страницами восемь условных сайтов, по шесть страниц
у каждого. Открытие страницы создаёт 16 запросов: четыре к ресурсам, общим
для всех сайтов, четыре — общим для данного сайта и восемь — отдельным
для страницы. Страницы сайта обходятся по кругу; после 12 открытий происходит
переход к следующему сайту. Всего используется 420 разных объектов.

Циклы, последовательный проход и переходы между страницами не используют
случайность. Их повторение при разных начальных значениях генератора
не увеличивает число независимых наблюдений.

## 1. Влияние размера кеша на выбор алгоритма

Используется один уровень. Обращение к кешу бесплатно; каждый промах
вызывает одну загрузку из источника. Проверяются 30 вместимостей:

1, 2, 4, 8, 16, 24, 32, 35, 36, 37, 48, 64, 72, 96, 144, 145, 146, 192,
217, 256, 289, 290, 291, 384, 512, 768, 1024, 1159, 1160 и 1161 объект.

Соседние значения около 36, 145, 291 и 1160 позволяют проверить переходы,
при которых характерный набор запросов начинает целиком помещаться в кеше.

Для каждого вида запросов формируются последовательности по 20 000 обращений
с начальными значениями генератора 1–5. Для каждой вместимости выбираются
алгоритмы с минимальным средним числом загрузок по этим пяти запускам.
При равенстве в таблицах перечислены все победители.

Основная метрика:

```text
Загрузки на 1000 запросов = 1000 × число загрузок / число запросов
```

Значение 80 означает 80 загрузок и 920 попаданий на 1000 запросов.
Меньше — лучше. В таблицах приведено арифметическое среднее метрики по запускам.

## 2. Иерархия, приближённая к процессорной

В модели три уровня: верхний мал и дёшев в обращении, нижние вместительнее
и дороже. Общая вместимость фиксирована и равна 290 страницам.
Отношению 1:16:128 соответствует разбиение 2+32+256.

| Уровень | Максимальная вместимость | Стоимость одного обращения |
|---|---:|---:|
| L1 | 4 страницы | 1 |
| L2 | 64 страницы | 3 |
| L3 | 256 страниц | 10 |
| Внешняя память | Не ограничивается моделью кеша | 50 за загрузку |

Размер L1 выбирается из 1, 2 и 4; L2 — из 16, 32, 48 и 64.
L3 получает оставшуюся память. Размеры должны возрастать по уровням
и укладываться в ограничения. Эти условия дают восемь допустимых разбиений.
Сравниваются все поддерживаемые сочетания алгоритмов в каждом разбиении.

Для каждого из восьми видов запросов используются 20 000 обращений
и пять начальных значений генератора 1–5. Победитель определяется
по минимальной средней стоимости запроса, усреднённой по пяти запускам.

Стоимость складывается только по фактически посещённым уровням:

```text
Средняя стоимость запроса =
(обращения к L1 + 3 × обращения к L2 + 10 × обращения к L3
 + 50 × загрузки из памяти) / число исходных запросов
```

Попадание в L1 стоит 1, в L2 — 4, в L3 — 14.
Промах на всех уровнях стоит 64. Это условные единицы, а не измеренное время.
Дополнительного штрафа за отклонение размеров от отношения 1:16:128 нет.

Пределы вместимости — условия эксперимента, а не параметры конкретного
процессора. Модель не учитывает ограничения размещения адресов по наборам
кеша, предвыборку, одновременную обработку промахов и запись изменённых данных.

Диаграмма алгоритмов для разных запросов строится при одном разбиении
2+32+256. В каждой строке показано целое лучшее сочетание.
Для оценки пользы разных алгоритмов оно сравнивается с лучшим вариантом,
где на всех трёх уровнях используется один и тот же алгоритм.

Этот опыт не определяет оптимальное число уровней: первые два уровня
вмещают не более 68 страниц, поэтому разместить в них тот же объём
290 страниц при данных ограничениях невозможно.

## 3. Иерархия с бесплатным обращением к уровням

Рассматриваются общие вместимости 8, 16, 36, 64, 145 и 290 объектов.
Для каждой проверяются один, два и три уровня. Вместимости уровней —
положительные целые числа с заданной суммой, в любом порядке.
Ограничений 4/64/256 и требования отношения 1:16:128 нет.

Любое попадание имеет нулевую стоимость, полный промах — одну загрузку.
Число загрузок на 1000 запросов вычисляется по той же формуле,
что и для одноуровневого кеша.

Для каждого из десяти видов запросов конфигурации подбираются по одной
последовательности из 6000 обращений с начальным значением генератора 1.
Это точный минимум в заданном наборе алгоритмов и разбиений.
При равенстве выбирается меньшее число уровней, затем один из равных вариантов.

Представлены 58 сочетаний вида запросов и общего объёма из 60.
Для равномерных запросов и неравномерной популярности при объёме 290
результатов нет; утверждение о точном минимуме на них не распространяется.

### Обоснование сокращения перебора

Полный набор допустимых конфигураций учитывается без обязательного
моделирования каждой до конца. Применяются следующие правила:

1. Если при одинаковой вместимости два верхних варианта передают вниз
   одинаковую последовательность промахов, последующие уровни получают
   одну и ту же задачу. Для поиска минимума достаточно одного продолжения.
2. REF на всю оставшуюся вместимость задаёт нижнюю границу загрузок
   для оставшихся уровней. Если она не лучше найденного результата,
   такое продолжение не может уменьшить минимум.
3. Число загрузок при обработке последовательности не убывает.
   Последний уровень можно остановить, когда он уже достиг числа загрузок
   лучшей найденной конфигурации.
4. Если достигнут REF на весь общий объём, более низкое число загрузок
   невозможно и дальнейший поиск не требуется.

Эти правила сохраняют минимум числа загрузок. Для выбора минимального
числа уровней при равенстве трёхуровневое решение дополнительно сравнивается
с точным минимумом среди одно- и двухуровневых вариантов.

### Проверка на новых последовательностях

Выбранные конфигурации фиксируются и сравниваются на последовательностях
по 6000 запросов с начальными значениями генератора 2 и 3.
Алгоритмы и размеры повторно не подбираются. Сравниваются одноуровневая
и многоуровневая конфигурации, выбранные на исходной последовательности.
Следовательно, это проверка переноса преимущества, а не поиск нового оптимума.

```text
Экономия = загрузки выбранного одного уровня
          − загрузки выбранного многоуровневого варианта
```

В основных таблицах экономия нормирована на 1000 запросов.
В таблице проверки она указана за все 6000 запросов.
Положительное значение означает выигрыш нескольких уровней,
отрицательное — проигрыш, ноль — равенство.

Диапазон проверочной экономии — минимум и максимум двух наблюдений,
а не доверительный интервал. Строгий выигрыш на обеих новых последовательностях
свидетельствует о его сохранении в этих двух проверках, но не доказывает
преимущества при любой нагрузке. Повторы детерминированных запросов
не являются независимыми проверками.

## REF и проценты от эталона

REF знает всю последовательность запросов заранее и при необходимости
вытесняет объект, следующее обращение к которому произойдёт позже остальных.
Запрошенный отсутствующий объект обязательно загружается.
Такой алгоритм задаёт идеальный минимум загрузок при заданной вместимости;
будущие запросы обычному кешу недоступны.

В моделях с бесплатным обращением используется REF на весь общий объём.
Объединение содержимого всех уровней хранит не больше разных объектов,
чем сумма их вместимостей. Идеальный одноуровневый кеш такой вместимости
может обслужить запросы не хуже. Поэтому REF задаёт корректную нижнюю
границу и для исследуемой многоуровневой системы.

```text
Загрузки, % от REF = 100 × загрузки конфигурации / загрузки REF
```

В процессорной модели эталон — один кеш REF на 290 страниц с ценой
обращения 1 и загрузки 50. Его средняя стоимость равна:

```text
Стоимость REF = 1 + 50 × загрузки REF / число запросов
Стоимость, % от REF = 100 × стоимость конфигурации / стоимость REF
```

Этот эталон сочетает большую вместимость с дешёвым доступом и не описывает
идеальную трёхуровневую систему с её ограничениями и разными ценами уровней.
Процент относительно него нельзя трактовать как расстояние до оптимальной
процессорной иерархии.

В обоих случаях 100% означает равенство эталону, 150% — значение метрики
в полтора раза больше. Это процент от REF, а не процент отставания.
В одноуровневом и процессорном опытах проценты вычисляются для каждого
запуска и затем усредняются. В свободной модели процент рассчитывается
по суммарным загрузкам; для представленной серии подбора из одного запуска
различия между этими способами нет.

## Границы интерпретации

Разброс между пятью случайными последовательностями показывает чувствительность
к запросам, но не делает небольшие различия статистически доказанными.
Результаты приводятся отдельно по видам запросов; общего рейтинга
с произвольными весами нагрузок нет.

Время работы алгоритмов, расход служебной памяти и трудность реализации
отдельно не измеряются. Их нельзя выводить из числа промахов
или подменять количеством строк кода.

Последовательности первых двух опытов содержат 20 000 запросов,
свободной модели — 6000. Длина влияет на долю первых загрузок и на историю
алгоритма, поэтому численные результаты разных серий напрямую не сопоставляются.
Выводы об оптимальности относятся к указанным моделям, реализациям,
размерам и запросам.
