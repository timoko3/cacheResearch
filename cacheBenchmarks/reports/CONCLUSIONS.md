# Основные выводы исследования кешей

[Оглавление всех материалов](README.md) · [Проверка отчётов](VERIFICATION.md)

Есть три отдельных опыта. В первом опыте сравниваются алгоритмы вытеснения для одноуровневого кеша
при разной вместимости. Во втором — стоимость поиска в трёхуровневой иерархии
с ограничениями на вместимость каждого уровня.
Третий опыт сравнивает один, два и три уровня кеша при одинаковом общем объёме памяти,
без ограничений на размер отдельных уровней. Затраты на поиск объекта в кешах
не учитываются. Подбираются размеры уровней и алгоритмы вытеснения, при которых
реже приходится загружать объект из памяти за пределами кешей — когда его нет
ни на одном уровне.

Влияние вместимости одноуровневого кеша на оптимальную стратегию кеширования:
[сравнения алгоритмов вытеснения при разных размерах одноуровневого кеша](software.md).
[Отчёт об иерархии](hierarchy.md) посвящён распределению памяти
между уровнями. [Методика](METHODOLOGY.md) объясняет названия алгоритмов, запросы и формулы.

## Главный результат: размер действительно меняет выбор алгоритма

Возьмём одну и ту же последовательность, в которой часто используемый набор
объектов меняется каждые 2000 запросов. Для каждого размера выберем алгоритм
с наименьшим средним числом загрузок.

| Вместимость одного кеша | Лучший алгоритм | Загрузок на 1000 запросов |
|---:|---|---:|
| 32 объекта | LIRS | 236,64 |
| 64 объекта | LRU | 117,22 |
| 290 объектов | LFU | 94,37 |

Загрузка нужна, когда объекта нет в кеше. Например, 117,22 загрузки на 1000 запросов
означают, что примерно 883 запроса удалось обслужить из кеша. Меньше загрузок — лучше.

Это не правило «для 32 объектов всегда выбирай LIRS». При тех же 32 местах,
но с постоянной неравномерной популярностью объектов, лучше оказался LFU.
**Имеют значение и размер кеша, и порядок запросов.**

![Как меняется результат при увеличении кеша](software/size_details.png)

Слева видно, как меняется преимущество алгоритмов при росте вместимости.
Справа — цикл из 291 объекта. Для LRU переход от 290 к 291 месту уменьшает
число загрузок с 1000 до 14,55 на 1000 запросов: весь цикл начинает помещаться.
Оставшиеся загрузки — первые обращения к объектам при пустом кеше.

## Больше памяти не всегда означает меньше промахов у любой реализации

В искусственном примере переходов между страницами текущий LFU дал:

| Вместимость | Загрузок на 1000 запросов |
|---:|---:|
| 48 объектов | 501,80 |
| 64 объекта | 658,00 |
| 96 объектов | 441,00 |

Здесь увеличение с 48 до 64 мест ухудшило результат.
Это наблюдение для конкретной реализации и конкретных запросов.
Поэтому в новом отчёте показаны кривые, а не только один «лучший размер».
При изменении вместимости меняется история содержимого кеша и последующих вытеснений.

## Что изменилось в модели иерархии

Экспоненциальный штраф убран. Вместо него заданы пределы:
**L1 ≤ 4, L2 ≤ 64, L3 ≤ 256 страниц**, всего ровно **290 страниц**.
Разбиение 2+32+256 из исходного отношения 1:16:128 остаётся допустимым.
Большой L1 на 290 страниц — нет.

Эти пределы — условия исследования около исходного разбиения, не характеристики
реального процессора. Проверены восемь допустимых разбиений и все поддерживаемые
сочетания пяти алгоритмов.

Измеряется только **средняя стоимость запроса**. Проверки уровней стоят 1, 3 и 10,
загрузка из памяти — ещё 50. Попадание в L3 стоит 14, полный промах — 64.
Это условные единицы, а не измеренное время.

При смене часто используемого набора лучшим оказался вариант
**LIRS4 + LRU64 + LIRS222**, средняя стоимость **9,945**.
При постоянном часто используемом наборе — **LFU4 + LFU48 + LFU238**,
средняя стоимость **8,830**.
Единого победителя для любых запросов нет.

Прежний вывод «три уровня лучше одного» отозван: его почти заранее задавал штраф.
С новыми пределами один или два уровня вообще не вмещают те же 290 страниц.
Для сравнения числа уровней теперь есть [отдельная серия](unrestricted.md):
размеры свободны, проверки бесплатны, общий объём у вариантов одинаков.

## Что показывает новая диаграмма уровней

График перераспределения памяти убран. Вместо него показаны целые сочетания
алгоритмов для каждого паттерна при одинаковых размерах **2+32+256**.

![Сочетания алгоритмов по уровням](hierarchy/strategies_by_level.png)

Разные алгоритмы в строке не обязательно дают большой выигрыш.
При смене горячего множества сочетание **LFU → LIRS → LFU** снизило среднюю
стоимость с **11,564** до **11,058** по сравнению с лучшим одинаковым алгоритмом
на всех уровнях. Для горячих объектов со сканированием разница всего
**19,583 против 19,580**. Для цикла из 145 объектов одинаковый LIRS даёт
тот же минимум, что показанное на рисунке сочетание.

Поэтому диаграмма сопровождается численным сравнением, а все равные лучшие
сочетания сохранены отдельно. Столбцы нельзя оптимизировать независимо:
запросы L2 зависят от промахов L1.

## Что меняется, если проверка всех уровней бесплатна

В [отдельной серии](unrestricted.md) фиксируется только
общий объём. Размеры уровней могут идти в любом порядке, ограничений 4/64/256 нет.
Перебираются все целочисленные разбиения на один, два и три уровня и пять алгоритмов
на каждом. Метрика — загрузки на 1000 запросов.

Завершены 58 из 60 запланированных точек. Равномерные случайные запросы
и неравномерная популярность при объёме 290 пока пропущены: расчёты остановлены
из-за длительности. В таблицах и графиках эти места явно отмечены;
выводы о точном минимуме относятся только к завершённым точкам.

Для искусственных переходов между страницами получились такие результаты:

| Общий объём | Выбранная конфигурация | Загрузок за 6000 запросов | Лучший один уровень |
|---:|---|---:|---:|
| 64 | LRU(56) → LIRS(8) | 1627 | 1644 |
| 145 | LRU(56) → LIRS(89) | 1384 | 1644 |
| 290 | LRU(56) → LIRS(234) | 952 | 1356 |

При 290 объектах несколько уровней дали на **404 загрузки меньше**.
Третий уровень для этого результата не нужен: при равном числе загрузок
теперь выбирается меньшее число уровней.

Размер 56 здесь имеет содержательное объяснение. Один условный сайт использует
4 общих ресурса, 4 своих общих ресурса и по 8 ресурсов у каждой из 6 страниц:
всего 56. LRU(56) обслужил 4356 запросов. До второго уровня дошли только 1644;
LIRS(234) обслужил ещё 692, оставив 952 загрузки из источника.
Это показывает пользу сочетания алгоритмов на данном паттерне.

### Минимум на одной последовательности не равен устойчивому преимуществу

Новая точная серия использует 6000 запросов и начальное значение генератора 1.
Выбранные варианты дополнительно проверяются на значениях 2 и 3 без нового подбора.
В отчёте отдельно показано, сохраняется ли выигрыш.

Например, при неравномерной популярности и объёме 36 вариант
**LFU(2) → LFU(34)** сэкономил 20 загрузок при подборе и 19–54 на двух новых
последовательностях. При объёме 16 преимущество выбранного сочетания меняло знак:
от проигрыша в 143 загрузки до выигрыша в 74.
Поэтому нельзя выбирать число уровней только по факту победы на одной трассе.
Здесь «трасса» означает записанную последовательность запросов.

Для переходов между страницами смена начального значения ничего не меняет.
Повтор того же детерминированного потока не считается независимым подтверждением.
Это искусственный пример, а не измерение настоящего браузера.

Для завершённых точек точный минимум найден **среди пяти проверенных алгоритмов
и всех допустимых разбиений заданного объёма на 1–3 уровня**.
Во всех 58 точках достаточно одного или двух уровней: третий не уменьшает
число загрузок по сравнению с лучшим вариантом с меньшим числом уровней.
Абсолютный идеальный предел при бесплатной проверке — REF на весь объём:
иерархия не может хранить больше разных объектов, чем эта вместимость.
Без знания будущих запросов достигнуть этого предела удаётся не всегда.

## Насколько программный опыт похож на браузерный кеш

Добавлены запросы с неравномерной популярностью и пример повторного использования
ресурсов при переходах между страницами. Есть загрузка своей последовательности
идентификаторов из файла через `--trace`.

Но это сравнение алгоритмов вытеснения объектов **одинакового размера**.
Правила HTTP, разные размеры файлов, свежесть ответов и время сети не моделируются.
Результат нельзя выдавать за сравнение настоящих браузеров.

## Что проверено

В исходных двух сериях: 20 000 запросов на последовательность, пять начальных значений
генератора, 30 размеров одного кеша. У программного кеша десять видов запросов,
у иерархии восемь. Данные отдельных запусков сохранены в CSV.

Прошли 127 C++ тестов и 12 Python проверок, полный короткий запуск старого
бенчмарка с `--output` и запуск нового на собственном файле запросов.

Исходный `cache_benchmark.py` сохранён отдельно на 64 страницы.
Новый код разделён на генерацию запросов, запуск C++ программы, расчёт показателей
и построение отчёта. Реализации алгоритмов в `cache.h` не менялись.
